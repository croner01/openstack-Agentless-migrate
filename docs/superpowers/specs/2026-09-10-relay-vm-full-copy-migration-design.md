# 中转机全量迁移设计（商业集中式存储 iSCSI/FC）

日期：2026-09-10
状态：待审阅

## 1. 背景与目标

现有迁移链路只覆盖 Ceph 后端：`ceph_utils` 直接替换卷背后 RBD 对象的数据面
（`replace_rbd_data`、`precopy_volume`、`finalize_incremental_volume`）。
商业集中式存储（华为、浪潮、宏杉、NetApp、PowerStore 等）通过 iSCSI/FC 把 LUN
挂到计算节点，卷没有可寻址的 RBD 对象，现有数据面通道无法使用。

本设计新增一条与底层存储解耦的数据通道：在源、目标两侧各启动专用中转机，
用 OpenStack 原生能力完成快照派生、卷挂载与卸载，由两侧 agent 在 IP 网络上
做块级全量拷贝。全过程无人值守，不产生手工操作。

目标：

- 不依赖具体存储厂商，只用 OpenStack API（Cinder/Nova）与块设备读写；
- 中转机在整个作业期间复用，避免逐 VM 反复创建；
- 派生卷、目标卷、快照、中转机的生命周期全自动，任务结束不堆积；
- 平台重启后仍能对账并回收孤儿资源；
- 页面上可配置、可监控、可取消。

## 2. 范围

### 范围内

- 商业集中式存储卷的全量块拷贝迁移；
- 作业级中转机池的创建、复用、健康检查与销毁；
- agent 注册协议、任务下发、进度上报、取消；
- 卷生命周期状态机、台账持久化、reaper 对账；
- 页面新增通道选择、池配置与池监控；
- 停机点快照与派生卷。

### 范围之外

- 增量拷贝、CBT、阵列远程复制（本设计明确不做，见第 12 节）；
- 运行中卷的在线预拷贝模式（会导致快照点之后的写入静默丢失，见 8.1）；
- 对源卷执行 detach，或任何变更源 VM 卷挂载状态的操作；
- 源 VM 自动删除；
- 中转机常驻池（跨作业复用）；
- 平台重启后的任务续跑（只做资源对账清理，不恢复任务进度）；
- 传输加密与静态加密；
- 非卷启动（ephemeral/本地盘）VM 的数据迁移。

## 3. 总体架构

控制面全部运行在现有 Flask 进程内：

| 模块 | 职责 |
| --- | --- |
| `relay_manager.py` | 中转机创建、注册等待、销毁、重建 |
| `relay_registry.py` | agent 注册表：role、状态、心跳、上报设备 |
| `relay_scheduler.py` | 池调度：把待拷卷派给空闲中转机 |
| `relay_ledger.py` | 台账持久化与加载（落 `uploads/`） |
| `relay_reaper.py` | 周期性对账与孤儿清理 |
| `transfer_task.py` | 卷级拷贝任务模型：阶段、偏移、限速、重试 |
| `openstack_utils.py` | 扩展建/删 server、attach/detach volume |

数据面是一台专用中转机镜像，内置 `relay-agent`（systemd 常驻）。

```
平台（控制面）
  ├── 源云 OpenStack API ──► 源中转机(agent)
  └── 目标云 OpenStack API ─► 目标中转机(agent)
                                    ▲
      源中转机 ══ 块流 TCP（数据面）═╝
```

控制面只传指令与进度，数据面由两台 agent 直连，平台不承载数据流量。

## 4. 中转机池

- 池为**作业级**：作业创建时建立，作业结束销毁。
- 池按 **(云, AZ)** 分组。Cinder 卷只能挂到同 AZ 的实例上，多 AZ 环境即多组池。
- 每台机器同一时刻只服务**一个卷对**（1 个源设备 + 1 个目标设备），复用方式为串行。
  同时刻在途派生卷数量上限约为 `2 × min(源池, 目标池)`，作为 Cinder 配额估算依据。
- 作业开始前**预热**：池内所有 agent 注册为 `ready` 后才开始派活，
  避免拷贝进行到一半才发现某台机器起不来。
- 心跳超时（默认 30s）标记 `unhealthy`，其上运行的任务判失败并换机重试，
  同时销毁并重建该机器。
- 池规模、flavor、镜像、网络、AZ 全部由页面配置，取值来自两侧云的真实数据。

## 5. 中转机生命周期与注册

创建时由 cloud-init 注入四项：平台地址、一次性注册令牌、`job_id`、`role`
（`source` / `target`）。agent 启动后主动向平台注册；平台不主动连中转机，
因此两侧安全组只需放通出方向。

状态流转：

```
provisioning → registered → ready → busy → ready（任务结束）
                                  ↘ draining → deleted
                                  ↘ unhealthy → deleted → provisioning
失败保留：failed_retained（仅失败任务，供排查）
```

注册令牌绑定 `job_id` + `role`，短有效期，注册成功即失效，换取会话 ID。
镜像携带 `agent_version`，注册时与平台做协议版本握手，不匹配则拒绝注册并把
原因写入任务日志。

## 6. Agent 接口协议

agent 只发起出向请求，取消指令通过心跳或领任务的响应体下发。

| 方法 | 路径 | 用途 |
| --- | --- | --- |
| POST | `/api/relay/register` | 令牌换会话，上报版本、IP、设备清单 |
| POST | `/api/relay/heartbeat` | 心跳，响应体可携带 `cancel` 指令 |
| GET | `/api/relay/tasks/next` | 长轮询领取任务 |
| POST | `/api/relay/tasks/<id>/progress` | 上报已传输字节与速率 |
| POST | `/api/relay/tasks/<id>/result` | 上报成功/失败与错误原因 |

数据面协议（agent 之间）：目标端固定监听端口（默认 9200），源端主动连接。
协议为分块帧 `magic | offset | length | crc32 | payload`，块大小 4 MiB，
两端均用 `O_DIRECT` 读写。握手携带平台下发的一次性任务票据，目标端校验通过
才接受连接；票据与任务绑定，任务完成即作废。

## 7. 卷生命周期与状态机

卷任务阶段：

```
queued → snapshotting → cloning → attaching_source → attaching_target
       → copying → detaching → finalizing → cleaning → done
```

任一阶段失败即进入 `failed`，失败处理见第 8 节。

责任边界：**agent 不做 attach/detach**。挂载与卸载全部由平台调用 OpenStack API
完成，agent 只接收设备路径与偏移区间。这样卷的生命周期只有一个责任主体，
不会出现 agent 与平台同时操作同一块卷的竞态，agent 也不需要持有任何云凭据。

台账（`relay_ledger`）每个卷任务一条记录，字段至少包含：

```
job_id / vm_id / volume_id / snapshot_id / derived_volume_id / target_volume_id /
source_relay_id / target_relay_id / phase / copied_bytes / attach_state /
created_at / updated_at / retry_count
```

**凡创建必登记**，这是不堆积的前提。台账写入
`uploads/relay-ledger-<job_id>.json`（0600），每次阶段变更落盘；服务启动时
加载全部未完成台账并触发一次 reconcile。

reaper 周期对账做三件事：

1. 中间态停留超时（例如 attach 超过 10 分钟）的卷任务，走 detach → delete；
2. 作业已结束但资源仍在的，全部回收；
3. 池内中转机的**实际 attachment 与台账比对**，台账中没有的 attachment 视为孤儿并清理。

作业结束（成功、失败、取消）统一执行一次全量 reconcile。

失败语义，与现有"失败保留资源"显式区分：

- 目标卷失败时**保留**，供排查；
- 派生卷与源快照失败时**一律清理**，它们可随时重建；
- 中转机失败时保留，成功后销毁。

## 8. 拷贝执行细节

### 8.1 停机窗口与快照

全量拷贝没有变化块跟踪，无法在停机窗口内只补增量。因此停机窗口与拷贝时长直接
绑定，只提供一条流程：

```
停源 VM → 打快照 → 派生卷 → 全量拷贝 → detach 派生卷与目标卷 → 启动目标
```

停机窗口约等于全量拷贝时长，TB 级大卷需按此规划窗口。

**已评估并移除的方案**：运行中打快照、拷贝完成后再停源 VM 切换可以显著压缩停机，
但目标会回滚到快照点，快照之后的所有写入静默丢失。这个正确性依赖业务方对"拷贝
期间该卷无写入"的人工保证，与无人值守、自动化迁移的目标冲突，且失败是静默的，
因此不作为用户可见模式提供。要压缩停机窗口只能走增量方案（CBT/阵列复制），
见第 12 节。

快照派生是唯一路径：源卷在源 VM 停机后依然处于 in-use（attachment 未解除），
Cinder 不允许再把它挂给中转机，因此必须由快照派生出一份独立、可自由挂载的拷贝源，
同时保留源卷及其 attachment 用于回滚。本设计**不 detach 源卷**——那会变更源 VM
的卷挂载状态。因此预检必须确认源端驱动支持对 in-use 卷打快照，不支持时该卷直接
判为不可迁移，不走任何降级路径。

### 8.2 执行细节

- 源 agent 从派生卷读取、目标 agent 写入目标卷，偏移与长度由平台下发；
- 限速为发送端令牌桶，平台可在运行中下发新的限速值；
- 进度双端上报：源端报已发送字节与速率，目标端报已落盘字节，两者不一致即告警；
- 断点续传成立的前提是**派生卷不可变**：同一偏移重复写入的数据相同，重试幂等。
  游标记在台账的 `copied_bytes`，中断后从最后确认偏移继续；
- 完成校验按代价递增：容量（目标 ≥ 源，硬门槛）→ 扇区大小一致 →
  尾部若干 MiB 哈希比对 → 整卷 sha256（按需开启）；
- 一致性：快照在源 VM 停机后创建，不依赖 `fsfreeze`、`qemu-guest-agent`
  或开机日志重放；源 VM 在整个拷贝期间保持停机，直到目标验证通过，保留回滚能力。

失败处理矩阵：

| 场景 | 处理 |
| --- | --- |
| agent 注册超时 | 销毁并重建中转机 |
| attach 失败 | 重试，仍失败则换一台中转机 |
| 拷贝中断 | 从 offset 续传，重试上限可配 |
| 目标 agent 崩溃 | 重建目标中转机、重新 attach、续传 |
| 容量或配额不足 | 预检拦截，不进入拷贝 |
| 源端驱动不支持 in-use 卷快照 | 预检拦截，该卷判为不可迁移，无降级路径 |
| 平台重启 | 加载台账并 reconcile，清理孤儿；不恢复任务进度 |

## 9. 配置项

按作业配置，高级项提供默认值：

| 配置 | 默认 | 说明 |
| --- | --- | --- |
| 数据通道 | RBD 直连 | `rbd` / `relay`，可逐 VM 覆盖 |
| 源/目标中转机镜像 | 无 | 从对应云镜像列表选择 |
| 源/目标中转机 flavor | 无 | 从对应云 flavor 列表选择 |
| 源/目标池大小 | 2 | 单侧机器数 |
| 中转机 AZ | 无 | 池按 AZ 分组 |
| 管理网 / 存储网 | 无 | 中转机接入的网络 |
| 单机限速（MiB/s） | 0 | 0 为不限速 |
| 注册超时 | 300s | 超时判失败并回收 |
| 心跳间隔 / 超时 | 10s / 30s | 健康判定 |
| 拷贝重试次数 | 3 | 超限标记该卷失败 |
| 整卷校验 | 关闭 | 关键卷可开 |

不新增第四步，改动落在现有三步向导内。

- **步骤 1** 新增"中转机池"面板：数据通道选择、源侧池配置、目标侧池配置、

- **步骤 2** 每条 VM 卡片增加通道标识并支持逐台覆盖，
  同时提示目标卷类型与容量取整。
- **步骤 3** 改为两段式：上方是中转机池视图（横向卡片显示角色、AZ、IP、
  状态、当前卷任务、心跳时间；顶部为全局计数：在途派生卷、在途目标卷、已清理数），
  下方保留现有任务与卷进度。操作入口提供取消任务、重建中转机、手动触发对账清理。

## 12. 风险与未支持场景

- **不做增量带来的停机窗口**：CBT 与阵列复制依赖厂商 API，本设计不引入。全量
  拷贝无法在停机窗口内只补变化块，停机时长约等于全量拷贝时长，TB 级大卷需要按此
  规划窗口。要压缩停机窗口，必须回到增量方案。
- **传输未加密**：跨云块流目前是明文 TCP，内容为磁盘全量数据，
  后续需补充 TLS 或限定在专线内。
- **带宽独占**：多台中转机并行会打满存储网与跨云链路，
  必须靠限速与池大小共同约束。
- **镜像版本漂移**：两侧镜像需与平台协议版本匹配，升级必须成套进行。
- **强依赖 in-use 卷快照能力**：源卷不 detach，快照派生是唯一拷贝源。源端驱动
  若不支持对 in-use 卷打快照，该卷不可迁移，本设计不提供降级路径。
- **不依赖客户机内 agent**：快照在源 VM 停机后创建，不需要 qemu-guest-agent，
  Windows 与 Linux 处理方式一致。
- **平台单副本**：台账落盘解决了资源对账，但任务进度本身仍不跨重启恢复。
